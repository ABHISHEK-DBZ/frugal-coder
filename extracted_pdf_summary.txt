4.5 Custom privacy plugin
The second AI suggested implementing PreLLMHook  and PreRequestHook .
These are real Bifrost plugin interfaces. However, there is an important security distinction.
Bifrost's documentation describes PreRequestHook  as a once-per-request routing phase and PreLLMHook  as a per-provider-attempt hook. Custom
plugin failures can be logged as warnings rather than automatically rejecting the request. 
GitHub +2
Therefore, we should NOT depend on a custom plugin alone to enforce confidential mode.
Our stronger implementation:
1. Detect confidential repository status before creating a session.
2. Create a dedicated local-only Bifrost virtual key.
3. Allow only the configured local provider through its provider allowlist.
4. Reject cloud-provider requests in our independent policy engine.
5. Use a plugin for additional routing validation and audit logging where appropriate.
6. Fail closed if local inference is unavailable.
That means even if the agent receives a prompt such as:
The request cannot access a cloud provider through the confidential session's restricted credentials.
Security principle
The privacy policy must be enforced outside the LLM's control, at multiple independent boundaries.

documentation currently lists Linux and macOS support, with matching Go versions and architectures. Since our deadline is close, we should first

20. What will make Frugal Coder stand out?
Our winning story should be based on five measurable demonstrations:
Efficiency
Less unnecessary context, fewer tokens and lower cost per successful task.
Reliability
Provider failover with persistent session recovery.
Privacy
Confidential repositories never go to cloud inference.
Cost control
Spending limits enforced before every paid model request.
Safety
No unauthorized writes, shell commands or Git operations.
